# PDR-001: Wireframe Plan — SPIFFE X.509 Setup: Platform Engineer

**Status**: Proposed
**Date**: 2026-07-25
**Author**: Romeo Martinez
**Depends on**: [`example/03.pdrs/VLT-X509 Mining in SPIFFE Secrets Engine.md`](../../example/03.pdrs/VLT-X509%20Mining%20in%20SPIFFE%20Secrets%20Engine%20.md), [`showcase/showcases/spiffe-x509/config.tsx`](../../showcase/showcases/spiffe-x509/config.tsx) (Platform Engineer journey, Steps 1–5)

---

## Problem Statement

When a platform engineer needs to make workload identity available to application teams,
they have no purpose-built setup path inside Vault for SPIFFE X.509 issuance. The current
PKI engine path is undocumented for this use case and requires custom trust bundle code.
The SPIFFE Secrets Engine exists but has no onboarding wizard, no X.509 configuration
surface, and no verification step after setup. Platform engineers either give up and route
teams through PKI + bespoke scripts, or stall on evaluating SPIFFE entirely.

The job: *when onboarding a new application team to workload identity, I want to configure
a trust domain, a role, and verify the trust bundle in one guided sequence — so I don't
have to read docs in parallel or coordinate a separate PKI setup.*

---

## Design Constraints

- **Layout**: Use the standard Vault UI page shell — App Header + App Side Nav + main content area. No full-screen modals for multi-step flows; use the content area itself with a stepper.
- **Component library**: Helios DS only. No custom components where a Helios primitive exists.
- **Responsive**: Desktop-first (1280px+). Tablet breakpoint (768px) must not break the stepper or form layout; single-column fallback is acceptable.
- **Progressive disclosure**: Show only the fields required for the selected SVID type (X.509 vs JWT). Never surface both simultaneously unless the operator explicitly adds both.
- **Validation**: Validate on blur for text fields. Inline error messages below the field — not above. Prevent advancing to the next step until the current step passes validation.
- **Accessibility**: WCAG 2.1 AA. All form fields have visible labels. Error messages are linked to fields via `aria-describedby`. Stepper step states communicated via `aria-current` and `aria-label`.
- **Empty states**: Every list view (roles list, auth method mapping list) has an explicit empty state with a direct CTA to create the first item.
- **Trust bundle verification**: The final step must show a live status check, not a static "done" message.

## Story Specifications

### Story 1 — `SecretsEngineList` (`01-secrets-engine-list.tsx`)

**Entry point** for the Platform Engineer. Shows the Secrets Engines index page before SPIFFE is enabled.

| State | Description |
|---|---|
| `default` | Engine list with existing mounts (KV, PKI, SSH). No SPIFFE mount present. "Enable new engine" button visible in top-right. |
| `with-spiffe` | Same list, now including a `spiffe/` mount row with type badge "SPIFFE" and a link to its detail page. |

**Layout**:
- Page title: "Secrets Engines"
- Table: columns = Mount path / Type / Description / Access
- Top-right: primary Button "Enable new engine"
- Empty state not needed here (other engines already exist)

**Interaction note**: Clicking "Enable new engine" → navigates to Story 2. Clicking an existing `spiffe/` row → navigates to engine detail (out of scope for this PDR, but the row must be present in the `with-spiffe` state).

---

### Story 2 — `EnableEngineModal` (`02-enable-engine-modal.tsx`)

**Step 0** of the setup flow. Operator picks the engine type and mount path.

| State | Description |
|---|---|
| `default` | Engine type selector. SPIFFE appears in the list as a selectable card alongside KV, PKI, Database, etc. Nothing selected. |
| `spiffe-selected` | SPIFFE card is highlighted. Mount path field pre-filled with `spiffe`. Description field optional. "Enable engine" primary button enabled. |
| `path-conflict` | Mount path field shows inline error: "A secrets engine is already mounted at this path." Enable button disabled. |

**Layout**:
- Full-page flow (not a modal — uses Vault's standard "Enable secrets engine" page)
- Step indicator at top: "Method" (active) → "Configuration"
- Engine type: grid of selectable cards (icon + name + short description)
- Below the grid: "Mount path" TextInput, "Description" TextInput (optional)
- Button Set at bottom: Cancel (secondary, left) / "Method" back link / "Next: Configuration" (primary, right) — disabled until engine type selected

**Helios components**: `RadioCard` grid (or `Card` with selection state), `Form::TextInput`, `ButtonSet`, `Alert` (inline, for path conflict)

---

### Story 3 — `EngineConfig` (`03-engine-config.tsx`)

**Step 1** of the setup flow. Configure trust domain and PKI backing. This is the first form the operator sees that is specific to SPIFFE X.509.

| State | Description |
|---|---|
| `default` | Form with all fields empty. Helper text visible under each field. |
| `filled-valid` | Trust domain `corp.example`, PKI issuer selected, bundle refresh hint `3600`. All fields valid. "Save configuration" button enabled. |
| `trust-domain-error` | Trust domain field contains a space or uppercase — shows inline error: "Trust domain must be a valid hostname (lowercase, no spaces)." |
| `issuer-missing` | PKI issuer path left empty after blur — inline error: "A PKI issuer path is required for X.509 SVID issuance." |
| `saving` | "Save configuration" button in loading state. Fields disabled. |
| `saved` | Inline Alert (success, neutral) below the form: "Trust domain configured. Trust bundle endpoint is now live." Button changes to "Next: Create a role →". |

**Layout**:
- Page header: breadcrumb `Secrets Engines / spiffe / Configuration`
- Section heading: "Trust Domain"
- Fields (in order):
  1. **Trust domain** — TextInput, required, helper text: "The SPIFFE trust domain for all SVIDs issued from this mount. Cannot be changed after the first SVID is issued. Example: corp.example"
  2. **PKI issuer path** — Select (populated from `pkiIssuers` fixture), required, helper text: "The Vault PKI engine issuer that will sign X.509 SVIDs."
  3. **Bundle refresh hint** — TextInput (number), optional, default `3600`, helper text: "How often (seconds) verifiers should re-fetch the trust bundle."
  4. **SVID type** — RadioGroup: "X.509 SVIDs", "JWT SVIDs", "Both". Default: X.509. Selecting JWT-only hides the PKI issuer path field (progressive disclosure).
- Button Set: "Cancel" (secondary) / "Save configuration" (primary)

**Helios components**: `Form::TextInput`, `Form::Select`, `Form::RadioGroup`, `ButtonSet`, `Alert`, `Breadcrumb`

**Validation rules**:
- Trust domain: non-empty, matches `^[a-z0-9]([a-z0-9\-]{0,61}[a-z0-9])?(\.[a-z0-9]([a-z0-9\-]{0,61}[a-z0-9])?)*$`
- PKI issuer path: non-empty when SVID type is X.509 or Both
- Bundle refresh hint: integer ≥ 60 if provided

### Story 4 — `RoleCreate` (`04-role-create.tsx`)

**Step 2** of the setup flow. Create the first role for X.509 minting.

| State | Description |
|---|---|
| `default` | Empty form. Only X.509-relevant fields shown (SVID type locked to X.509 from engine config). |
| `filled-valid` | All required fields populated with values from `roleDefaults` fixture. "Create role" button enabled. |
| `template-error` | SPIFFE ID template missing `spiffe://` prefix — inline error: "Template must produce a valid SPIFFE ID starting with spiffe://" |
| `ttl-error` | Max TTL less than TTL — inline error on max TTL: "Max TTL must be equal to or greater than TTL." |
| `saving` | Button in loading state. |
| `saved` | Inline success Alert: "Role k8s-worker created. Workloads using this role will receive X.509 SVIDs with a 1h TTL." Link "Create another role" and "Next: Attach auth method →". |

**Layout**:
- Page header: breadcrumb `Secrets Engines / spiffe / Roles / Create`
- Section heading: "Role Configuration"
- Fields (in order):
  1. **Role name** — TextInput, required. Example: `k8s-worker`
  2. **SVID type** — read-only display "X.509" (inherited from engine config, not changeable here)
  3. **SPIFFE ID template** — Textarea (monospace), required. Helper text: "Use `{{.entity.aliases.<auth_method>.metadata.<key>}}` to interpolate workload metadata. Must produce a URI starting with spiffe://<trust-domain>/". Below the field: rendered preview line once template is non-empty: "Preview: spiffe://corp.example/k8s/..."
  4. **TTL** — TextInput. Default `1h`. Helper text: "Lifetime of issued X.509 SVIDs. Short-lived is recommended (1h or less)."
  5. **Max TTL** — TextInput. Default `24h`. Helper text: "Maximum TTL a caller can request. Leave blank to use the engine default."
  6. **Key algorithm** — Select: EC (P-256), EC (P-384), RSA-2048, RSA-4096. Default: EC (P-256).
- Button Set: "Cancel" (secondary) / "Create role" (primary)

**Helios components**: `Form::TextInput`, `Form::Textarea`, `Form::Select`, `Badge` (SVID type read-only), `ButtonSet`, `Alert`

---

### Story 5 — `AuthMethodMapping` (`05-auth-method-mapping.tsx`)

**Step 3** of the setup flow. Attach an existing auth method to the role via Vault policy.

| State | Description |
|---|---|
| `empty` | No mappings yet. Empty state: "No auth method attached. Attach one to allow workloads to mint SVIDs." with "Attach auth method" CTA. |
| `method-selected` | Dropdown open showing existing auth methods from `existingAuthMethods` fixture. |
| `policy-preview` | After selecting auth method and role, shows a read-only HCL policy block: `path "spiffe/role/k8s-worker/mintx509" { capabilities = ["update"] }`. "Copy" button next to block. Below: "Apply this policy to your auth method role configuration." |
| `attached` | Table row: auth method `kubernetes/` → role `k8s-worker` → policy `workload-identity`. Status badge "Active". "Remove" tertiary button on row. "Attach another" link below table. |

**Layout**:
- Page header: breadcrumb `Secrets Engines / spiffe / Roles / k8s-worker / Auth Methods`
- Section heading: "Auth Method Mappings"
- Note text (Alert, neutral): "Vault reuses existing auth method configurations. No new attestation infrastructure is required."
- When `empty`: Application State component (empty) with icon + message + CTA button
- When `attached`: Table with columns: Auth Method / Role / Policy / Status / Actions

**Helios components**: `Form::Select`, `ApplicationState`, `Table`, `Badge`, `CodeBlock` (read-only HCL), `ButtonSet`, `Alert`

---

### Story 6 — `TrustBundleVerify` (`06-trust-bundle-verify.tsx`)

**Step 4** of the setup flow — the final confirmation. Operator verifies the trust bundle is reachable and correct before handing the role off to app teams.

| State | Description |
|---|---|
| `checking` | Spinner + "Checking trust bundle endpoint..." message. |
| `success` | Green-bordered (or success badge) summary card: trust bundle URL, key count (2), CA fingerprint, replica sync status "Synced", last fetched timestamp. "Done — share with your app teams" primary Button. Below: copyable text block with the bundle URL and role name for handoff. |
| `unreachable` | Alert (critical): "Trust bundle endpoint is not reachable from this browser. Verify your Vault listener is accessible at `https://vault.corp.example/v1/spiffe/bundle`." Retry button. |
| `empty-bundle` | Alert (warning): "Trust bundle returned 0 keys. Verify the PKI issuer path in engine configuration." Link "Go to configuration". |

**Layout**:
- Page header: breadcrumb `Secrets Engines / spiffe / Trust Bundle`
- Section heading: "Trust Bundle Verification"
- Description text: "Verifiers (Envoy, cloud IAM, other Vault clusters) will fetch this endpoint to validate SVIDs offline. No Vault token is required to access it."
- Verification result card (when success):
  - Bundle URL (copyable)
  - Keys in bundle: `2`
  - CA fingerprint (truncated, expandable)
  - Replica sync: badge "Synced" / "Pending"
  - Last fetched: ISO timestamp
- Handoff block (when success): monospaced text with role name, trust domain, and bundle URL — with "Copy" button. Label: "Share with your application team."

**Helios components**: `Alert`, `Badge`, `CodeBlock`, `ButtonSet`, `Spinner` (or loading state), `Card`/`Table` for summary

## Storybook Conventions

- **Story file**: `pe-spiffe-setup.stories.tsx` — one file, all 6 components exported as named stories.
- **Story naming**: `ComponentName/StateName` (e.g., `SecretsEngineList/Default`, `EngineConfig/FilledValid`).
- **Fixture imports**: All fixtures from `pe/_fixtures.ts`. No inline data in story files.
- **Viewport**: Default `1280x800`. Add `tablet` viewport story for `EngineConfig` and `RoleCreate` to validate single-column fallback.
- **No actions library**: Use `fn()` from `@storybook/test` for button click handlers.
- **Component props**: Each component accepts a `state` prop (string union of state names) to switch between visual states without interaction.

## QA Checklist

**Per component:**
- [ ] All states defined in the story spec are present and visually distinct
- [ ] Error states show the exact error message text from this PDR
- [ ] No hardcoded pixel values — use Helios spacing tokens
- [ ] All interactive elements (buttons, selects, inputs) have visible labels
- [ ] Empty state has a direct CTA that matches the described action

**Flow continuity:**
- [ ] Breadcrumb in each story matches the described path
- [ ] "Next" CTAs in each story reference the correct subsequent step
- [ ] `with-spiffe` state in Story 1 shows the engine that would result from completing Stories 2–3

**Trust bundle verification:**
- [ ] `success` state shows both key count and replica sync status
- [ ] `unreachable` state gives the full endpoint URL in the error message
- [ ] Handoff block in `success` state contains trust domain, role name, and bundle URL — all three

**Progressive disclosure:**
- [ ] Selecting "JWT SVIDs only" in Story 3 (`EngineConfig`) hides the PKI issuer field
- [ ] SVID type in Story 4 (`RoleCreate`) is read-only and reflects the engine config choice
