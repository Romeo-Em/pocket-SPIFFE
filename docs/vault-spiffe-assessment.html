Vault SPIFFE - An Honest Assessment

A problem-by-problem review of whether Vault's SPIFFE work actually addresses the gaps described in the "Everyone Wants SPIFFE" critique — and an equally direct account of where it doesn't.

What this doc is

The critique document argues that SPIFFE is a good standard but SPIRE is a multi-year infrastructure project that leaves the SaaS boundary, legacy applications, on-premises attestation, CI/CD, federation, and AI agent identity largely unsolved. This doc goes through each of those ten problems and asks, honestly: does Vault's SPIFFE work address it, partially address it, or not address it at all. Where Vault's own internal docs disagree with each other about how much is done, that's called out directly rather than resolved in Vault's favor.

Who should read this: anyone deciding how to position Vault SPIFFE externally, and anyone deciding what to build next. This is not a marketing document. Several claims made in Vault's own positioning and vision docs are contradicted by its own milestone and priority docs, and that gap matters more than the pitch.

Clarification the source docs don't make cleanly

"Vault SPIFFE" is not one feature

Across the strategy docs it refers to at least four different things, and conflating them is the single biggest risk to an honest external claim:

  1. SPIFFE Secrets Engine — Vault Enterprise, ships today. Mints JWT-SVIDs only. X.509 SVID minting is a proposed PRD (VLT-515), not shipped.
  2. SPIFFE Auth Method — Vault Enterprise, ships today. Consumes JWT- or X.509-SVIDs (from Vault or from an existing SPIRE deployment) and exchanges them for a Vault token.
  3. Vault as a SPIRE replacement / standalone identity provider — node and workload attestation, direct SVID issuance without a Vault token, a Workload API socket, trust bundle hosting for X.509. This is the aspirational vision described in vault-as-spiffe-provider-priorities.md, -milestones.md, and spiffe-identity-provider-vision.md. It is a roadmap, not a shipped product.
  4. Vault as a federation participant — the auth method can consume a trust bundle from an existing SPIRE Federation endpoint; the secrets engine hosts a JWT trust bundle other systems can trust. X.509 federation with SPIRE is explicitly out of scope until X.509 SVID support ships.

Any claim below that says "Vault solves X" should be read as applying to a specific one of these four, not to "Vault SPIFFE" as an undifferentiated whole.

01

The ecosystem complexity problem

The critique

Production SPIRE requires 8-10 separately maintained components (server/agent, SPIFFE-Helper, CSI driver, Controller Manager, Envoy/SDS, service mesh, OPA, cert-manager, Tornjak, HSM/KMS, monitoring).

What Vault claims

The proposed vault-spiffe-server binary would fold the secrets engine, trust bundle hosting, TPM/cloud/k8s attestation, workload attestation, SVID-direct issuance, and a Vault Agent Workload API socket into one deployable unit. spiffe-identity-provider-vision.md frames this directly as "the operational reach of SPIFFE without the burden of operating SPIRE."

What's actually true today

That binary is Milestone 4, explicitly described as "not a near-term deliverable." Today, using Vault SPIFFE means running full Vault Enterprise, which is not a lighter operational footprint than SPIRE for a customer who doesn't already run Vault. For existing Vault customers, the marginal component count is lower — but that's a claim about existing customers, not a claim that Vault SPIFFE is inherently simpler than SPIRE.

Not solved

Vault doesn't replace Envoy/SDS, a policy engine equivalent to OPA (Vault's HCL policy is a different mechanism serving a different layer), cert-manager, or a Tornjak-equivalent multi-cluster visibility tool. The vision doc's own "visibility & reporting" item is listed as unbuilt.

Honest read

The consolidation story is real for the mTLS-light, JWT-only use case, and aspirational for everything else. Since the critique itself notes that mTLS-based workload identity is "the majority of real SPIFFE deployments," and Vault's X.509 story doesn't ship until ~January, this claim is weaker than the vision docs suggest today.

02

The SaaS problem

The critique

SPIFFE has no path to Snowflake, Salesforce, GitHub, or Okta because those services speak OAuth and API keys, not SVIDs.

What Vault claims

Nothing, directly. No file claims an SVID can authenticate to a third-party SaaS product.

What's actually true

Vault's answer is adjacent, not native. A workload presents its SVID to Vault, and Vault's separate, non-SPIFFE dynamic secrets engines can then issue database credentials, cloud credentials, or PKI/SSH certs. This doesn't cross the SaaS boundary the critique describes — it's Vault's general-purpose secrets management capability, which exists independent of whether SPIFFE is involved at all.

Not solved

There is no SVID-to-OAuth exchange for Salesforce, Slack, GitHub, Okta, or Datadog anywhere in these docs. This is a direct concession, not a rebuttal, of the critique's point. The honest framing: "SPIFFE doesn't solve this, and neither does Vault SPIFFE — but Vault as a broader secrets manager has always run a parallel, non-SPIFFE track for these credentials, which is the same answer SPIRE-adjacent teams already use today."

03

The legacy application problem

The critique

Applications that can't call the SPIFFE Workload API (Java monoliths, .NET on bare metal, COBOL, vendor software) can't participate without a sidecar like SPIFFE-Helper.

What Vault claims

A future Vault Agent Workload API socket plus built-in Unix workload attestation (UID/GID/binary path) would let SPIFFE-native workloads and sidecars retrieve SVIDs from Vault Agent, similar to what SPIRE Agent + SPIFFE-Helper do combined.

What's actually true

This is entirely roadmap — Priority 3 and Priority 4 in vault-as-spiffe-provider-priorities.md, targeted for ~April. Nothing ships today that makes it easier for a legacy application to get an identity from Vault than from SPIRE. Vault Agent today still requires the workload to actively authenticate through a configured auth method, not a transparent local socket.

Not solved

No doc addresses vendor-locked or contractually-unmodifiable software specifically. Once the socket ships, the same fundamental problem the critique describes — a legacy binary has to discover and use a new local interface — still applies; Vault's version of this faces the identical adoption friction SPIFFE-Helper does today.

Honest read

There is currently no meaningful difference between Vault and SPIRE for this problem. Both require future engineering work the customer doesn't have today.

04

The on-premises problem

The critique

Node attestation is easy in the cloud (signed instance metadata) and weak on-prem, where SPIRE falls back to TPM-based attestation or brittle process-level selectors.

This is Vault's strongest, most substantiated claim. TPM 2.0-based attestation is the centerpiece of the on-prem story across nearly every strategy doc:

  • SPIFFE-Strategy.md: "TPM auth with attestation can solve Secret Zero for on-prem workloads."
  • vault-as-spiffe-provider-milestones.md: "Vault Agent on a Linux VM uses the TPM 2.0 EK to prove the node's identity to Vault. No static bootstrap secret."
  • SPIFFE Case Studies — Trends & Patterns.md names on-prem attestation as "the dominant gap across all case studies," and states this is "precisely the gap TPM-backed hardware attestation in Vault addresses."
  • Real customer signal: DBS meeting notes describe the customer as "looking more closely at TPM-backed identity than SPIFFE today" and wanting a "TPM → SPIFFE workflow."
What's actually true

TPM node attestation is in development, targeting Vault 2.1 (~October). It is not shipped as of these docs. Even once it ships, the first output is a Vault token plus certificate, not an SVID — SVID-direct issuance for on-prem workloads doesn't land until Milestone 2 (~January). And the initial capability only attests the node, not distinct workloads running on that node — per-process workload attestation is a separate, later milestone (~April). Windows is explicitly out of scope; this is "Linux + vTPM only" for now.

Internal contradiction worth flagging

spiffe-vault-meeting-synthesis.md states Vault does "90% of what SPIRE does" with "one gap" (workload attestation) — a much rosier framing than vault-as-spiffe-provider-priorities.md, which lists six separate, still-substantial gaps (X.509 SVIDs, X.509 trust bundle, Workload API socket, workload attestation, SVID-direct, and the scoped binary). The "90%" figure should not be repeated externally without qualifying which slice of the SPIFFE surface it covers.

Honest read

Real customer demand exists and the hardware-rooted approach is technically credible, but it is not available today. Any external claim should say "in development, targeting Vault 2.1," not "solved."

05

The CI/CD pipeline problem

The critique

Ephemeral CI/CD runners don't run SPIRE agents by default, and reliable attestation for them is non-trivial.

What Vault claims

Nothing. None of the strategy, milestone, priority, or positioning docs mention GitHub Actions runners, GitLab CI agents, ephemeral pipeline identity, or OIDC-federation-for-CI as a target scenario at all.

Not solved

This is a complete, unaddressed gap in the current Vault SPIFFE narrative. The docs focus on agentic AI, on-prem VMs/bare-metal, and Kubernetes/cloud workloads — CI/CD pipelines are simply absent from the corpus. This should be stated plainly rather than papered over: Vault SPIFFE has no answer here today, and no roadmap commitment either.

06

The federation problem

The critique

Adding/removing trust domains requires config changes and restarts across every participant; JWKS key counts grow with the number of SPIRE servers and vendors impose undocumented limits (AWS STS ~100 keys, Confluent much fewer); Indeed Engineering hit real bugs debugging this in production.

What Vault claims

Trust bundle hosting for JWT ships today (OIDC well-known endpoint, .well-known/keys, trust_bundle/web). The SPIFFE auth method can already consume a trust bundle from an existing SPIRE Federation endpoint, meaning Vault can participate as a federation consumer today for the JWT lane.

What's explicitly not true

X.509 trust bundle hosting is a named, repeated gap. vault-spiffe-secrets-engine.md states plainly that federation with SPIRE is not possible today because it requires X.509 SVID support, which doesn't exist yet. The PRD for X.509 minting (VLT-515) puts federation with SPIRE explicitly out of scope for Milestone 1 — worth noting that the same PRD document also writes acceptance criteria for a federation requirement before excluding it, which is an internal inconsistency in the PRD itself, not just a gap.

Not solved at all

None of the critique's specific pain points (undocumented JWKS key-count limits, JWKS growth with multiple signing servers, the float-serialized-timestamp bug Indeed hit with AWS STS) are discussed anywhere in the Vault docs. Vault's Raft-HA cluster architecture may structurally reduce JWKS bloat compared to a federation of many independent SPIRE servers, but this is not analyzed or claimed anywhere — it would need real testing before being stated as a benefit.

Internal contradiction worth flagging

vault-spiffe-positioning.md's two-server architecture diagram assumes trust bundle interoperability with other Vault clusters and third parties as already functional, but this is only true for the JWT lane. Most SPIRE-federation customers care about the X.509/mTLS lane, where Vault's own secrets-engine doc says federation isn't possible yet.

07

The "deployment takes 6-24 months" problem

The critique

Defakto's own documentation says small SPIRE deployments take 6-12 months and complex ones 12-24 months, even with a dedicated expert team.

What Vault claims

Faster time-to-value, because "customers already have auth methods configured for attestation, and sets of policy" (PRD VLT-515 background) — i.e., existing Vault infrastructure gets reused rather than building SPIRE from zero. SPIFFE-Strategy.md states the explicit goal: "For most customers, Vault should remove the need to deploy and operate standalone SPIRE infrastructure."

What's actually true

For an existing Vault customer wanting JWT-SVIDs today, this is plausible and fast — Milestone 0 requires no new engineering. But the full provider vision (attestation, X.509, Workload API, workload attestation) spans four milestones from now through ~April, which is itself 9+ months of engineering before Vault reaches anything resembling SPIRE feature parity. Milestone 3 (~April) is the point explicitly described as "drop-in comparable to SPIRE" — meaning Vault's own team does not consider the product SPIRE-comparable before then.

Honest read

This is a real claim for a narrow use case (an existing Vault customer who only needs JWT-SVIDs) and an aspirational claim everywhere else. External positioning that speaks in the present tense ("Vault is the SPIFFE identity authority") without this qualifier would overstate what's true today.

08

Component maintenance risk (e.g. Tornjak)

The critique

SPIFFE ecosystem components have uneven maintenance quality — Tornjak's last major releases date to 2022-2023, with subsequent versions being mostly automated dependency bumps. Unmaintained security tooling accumulates risk over time (CNCF's own archival process exists because of this pattern).

What Vault claims

Nothing directly. No doc mentions Tornjak, CSI driver versioning, or release-cadence risk as a named consideration.

Not solved, not addressed

The closest thing to a response is implicit — consolidating capability inside a single, commercially-supported Vault Enterprise product plausibly reduces the "which of my nine components went stale" risk, since one vendor owns the release cadence. But this is not stated or analyzed anywhere in the corpus, and it cuts both ways: Vault's own new SPIFFE-provider subsystems are themselves new components Vault has to build and then maintain going forward. No doc discusses this self-critically.

09

The AI agent identity problem

The critique

Three categories of AI agent deployment (commercial AI with human-in-loop, custom agents with human-in-loop, fully autonomous agents) each have identity problems SPIFFE wasn't designed for — no concept of intent, delegation chain, or ephemeral task-scoped identity. Cites the Replit database-deletion incident and CSA survey data (only 23% of orgs have a formal agent identity strategy).

This is Vault's second-strongest, most substantiated claim.

  • A three-layer agentic access architecture is described in vault-spiffe-provider-use-cases.md: node attestation to JWT-SVID, then token exchange with an authorization server using Rich Authorization Requests (RAR) and on-behalf-of/May Act delegation, then a Vault resource server enforcing an Agent Registry with ceiling policies and full audit trail ("user → agent → tool → resource → action → decision").
  • This directly targets Category 2 (custom agents with human-in-loop): RAR claims and ceiling-policy intersection are designed to bound an agent's access to the immediate task and expire automatically.
  • The architecture is explicitly designed around the credential-aggregation attack surface the critique's Replit example illustrates: the agent should not carry broad standing credentials, and the per-request flow doesn't produce a durable Vault token.
  • Real customer interest exists: DBS meeting notes describe wanting "On-Behalf-Of (OBO) / May Act delegation flows" scaling to "10,000+ agents/workloads."
  • The Agent Registry and audit-trail model also partially targets Category 1 — the audit gap the critique names is addressed by the attribution model, if implemented.
What's actually true

The entire agentic architecture is private preview, not GA. There is no HashiCorp-native Authorization Server yet — vault-spiffe-provider-use-cases.md lists this as an open question, meaning the AS step currently depends on third parties (IBM Verify, Keycloak proof-of-concept), an external dependency Vault doesn't fully own. SVID-direct issuance for agents is a January-target milestone, not shipped.

Not solved

Category 3, fully autonomous agent-spawns-agent chains, is the weakest area even in Vault's own docs. No file discusses agent-to-agent delegation chains or the specific Solo.io concern quoted in the critique — "if identities are more fine-grained, and even potentially generated on the fly, how can you possibly write authorization policies around this?" Vault's ceiling-policy model bounds access for a known, registered agent; it doesn't clearly answer how policy gets written for identities generated dynamically at runtime.

Honest read

This is real, differentiated design work, further along conceptually than anything else in this document — but it's private preview, has an unresolved external dependency (the AS), and its own authors flag open architectural questions. It should not be described as solved.

10

The credential type gap

The critique

OAuth client credentials, database passwords, API keys, Kerberos tickets, SSH keys, and cloud access keys all sit outside the SVID model and need separate lifecycle management, running in parallel with SPIFFE.

What Vault claims — its strongest non-SPIFFE-native answer

"A workload presents its SVID to Vault... and Vault issues dynamic database credentials, cloud credentials, PKI certificates, SSH certs — short-lived, scoped, auto-rotated. No other SPIFFE provider also has a secrets engine" (vault-spiffe-provider-use-cases.md). SPIFFE-Strategy.md also describes explicit SVID-to-cloud-IAM exchange flows: AWS IAM Roles Anywhere via X.509 SVID, GCP Workload Identity Federation via JWT-SVID, Azure Workload Identity via JWT-SVID.

What this actually is

The SVID becomes an authentication input into Vault's pre-existing, non-SPIFFE dynamic secrets engines. This is honest and real, but it's precise to note: this is Vault (the broader secrets management product) solving credential-type diversity, not SPIFFE solving it.

Not solved

OAuth client credentials for SaaS (Salesforce, Slack, GitHub, Okta, Datadog) are not addressed — no SVID-to-OAuth-SaaS exchange exists. Kerberos tickets for on-prem Active Directory-integrated systems are not mentioned anywhere in the corpus.

Honest read

Vault's answer here doesn't refute the critique's underlying point — it confirms it. Every one of these credential types still needs separate lifecycle management. What Vault offers is that its secrets engines already do that management today, independent of how mature the SPIFFE work is. This is a legitimate differentiator versus SPIRE (which has no secrets engine at all), but it should be framed as "Vault, the platform, already solves credential diversity" rather than "SPIFFE solves credential diversity."

Summary

Bottom line

Vault SPIFFE has two genuinely strong, differentiated answers to the critique: hardware-rooted on-prem attestation via TPM, and a scoped, auditable model for AI agent access built on RAR and an Agent Registry. Neither is shipped today — TPM attestation targets Vault 2.1 (~October), and the agentic architecture is private preview with an unresolved dependency on a third-party authorization server. Both should be described as in-progress, not solved.

Vault's answer to the credential-type gap (SaaS, databases, cloud keys, SSH) is real but is a claim about Vault's general secrets management capability, not about SPIFFE itself — worth being precise about that distinction in any external framing, since it's easy to blur.

Several problems from the critique are not addressed anywhere in the current Vault SPIFFE corpus: the SaaS-authentication boundary itself, CI/CD ephemeral runner identity, Kerberos/on-prem AD integration, component maintenance risk, and the specific federation failure modes (JWKS key-count limits, trust bundle bugs) that the critique's Indeed Engineering example describes in detail.

Internally, Vault's own strategy docs don't agree on how far along this work is. The positioning and vision docs speak in the present tense about capabilities that the milestone and priority docs list as gaps targeting future quarters. The most reliable single source of truth in this corpus is the "grounding: what we actually have today" table in vault-as-spiffe-provider-milestones.md — any external claim should be checked against that table before it's made.

Unresolved

Open questions

  • Should the credential-type-gap section distinguish "Vault the secrets manager" from "Vault SPIFFE" more sharply in external materials, given how easily the two get conflated in the source docs themselves?
  • Who owns resolving the PRD VLT-515 internal inconsistency (federation requirement written with acceptance criteria, then excluded from Milestone 1 scope)?
  • Is there a plan to address CI/CD ephemeral identity at all, or is that intentionally out of scope for Vault SPIFFE's roadmap?
  • Should the AI agent architecture's dependency on a third-party Authorization Server be resolved before any external claim describes agentic access as differentiated, given it's not fully within Vault's control?
